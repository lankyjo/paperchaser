# Pitfalls Research

**Domain:** Browser-only, local-first invoice/quote/receipt document workspace (WYSIWYG builder + client-side PDF generation)
**Project:** Paperchaser
**Researched:** 2026-08-07
**Confidence:** HIGH (primary-source verified: react-pdf docs + GitHub issues, Dexie docs, Zustand docs, dnd-kit docs, vite-plugin-pwa docs, TanStack Start docs, MDN storage/eviction)

> This file is the pitfalls dimension feeding roadmap creation. For each pitfall: what goes wrong, why it happens, how to avoid, warning signs, and which phase addresses it. Phase names use the established "Phase 1 spike" convention; later phase names are logical labels the orchestrator maps onto the concrete phase list.

## Critical Pitfalls

Mistakes that cause rewrites, data loss, or a product that cannot ship.

### Pitfall 1: PDF preview/output mismatch — building two independent layout engines

**What goes wrong:**
The on-screen WYSIWYG canvas renders the document one way; the generated PDF renders it another. Text wraps differently, totals rows shift, a "one page" preview produces a two-page PDF, fonts differ, margins drift. PRD §6.9 ("identical preview/output") fails on every document with more than a few line items.

**Why it happens:**
The #1 root cause in this domain is architecting the preview and the PDF as *separate rendering pipelines*. The canvas must be HTML/CSS (the three-pane builder edits the DOM); if the PDF is generated by a second engine (@react-pdf/renderer, jsPDF, html2canvas), you maintain two layout engines that must agree pixel-for-pixel. They will not. @react-pdf/renderer explicitly uses **Yoga layout + pdfkit**, not browser CSS — its flexbox subset, text measurement, and Knuth–Plass hyphenation differ from the browser's. Every element is a potential divergence point. Its own docs confirm fonts/images are fetched asynchronously and *block layout until loaded*, so a preview rendered before fonts load gets wrong metrics and cannot match the PDF. The second root cause: re-rendering the full PDF on every keystroke (to make the preview "the real PDF") is too slow to edit against, so teams build a fast HTML preview and parity dies.

**How to avoid:**
**One document model, one rendering pass.** Make the document a pure serializable JSON tree (renderer-agnostic data model — non-negotiable under any engine choice). Then either:
- **(Recommended, Phase 1 spike decides)** Render the canvas as HTML/CSS and make the *same* HTML the print document via `@media print` + `@page` CSS. Parity is guaranteed by construction — the preview IS the print output. Cost: browser print-CSS fidelity (repeating table headers, mm margins, per-page watermarks) must be proven in the spike, especially Safari.
- **(Fallback)** If the spike proves print-CSS insufficient and @react-pdf/renderer stays: preview must render the actual react-pdf output (pdfjs-dist canvas or the react-pdf blob) at a throttled rate, or accept visible preview/PDF divergence. Do not ship "HTML preview + react-pdf output" side by side.

**Warning signs:**
- Any feature that must be implemented twice — once in the canvas, once in the PDF code.
- The canvas uses CSS `flex`/`gap`/`overflow` freely while the PDF component uses a different layout subset.
- Test documents with long company names, accented text, many line items: pagination agrees in preview but not in the downloaded PDF.
- Preview renders instantly but PDF download takes seconds (signature of the two-engine split).

**Phase to address:**
Phase 1 spike (PDF engine evaluation) — the single highest-risk decision in the product. Must produce an ADR for the render path plus a golden-image/snapshot test harness comparing preview vs PDF on a fixture set.

### Pitfall 2: Pagination breakage with @react-pdf/renderer — force-fit overlap, split table rows, missing repeat headers

**What goes wrong:**
Line items, section headers, and totals land at page boundaries and produce: content that overlaps itself at the break; a table row split mid-row; a header row orphaned at the bottom of page 1 while its rows flow to page 2; repeated header/footer columns that appear on page 1 only; a "Page 1 of 1" that is wrong once content grows.

**Why it happens:**
@react-pdf/renderer's pagination is an automatic wrapping engine with specific, surprising semantics (verified from official docs):
- Components are **breakable** (View/Text/Link) or **unbreakable** (Image only by default). A "table row" is just a View — breakable — so rows CAN split mid-row unless `wrap={false}`.
- `wrap={false}` forces the element to a new page if it doesn't fit — but there is a **known open bug (#3449)**: when a block lands near a page bottom with "just barely not enough room," react-pdf force-fits it into the remaining space and its lines are drawn overlapping at the break, wasting the rest of the page. It hits exactly the two-column rows and `wrap={false}` blocks (headers, table rows) an invoice is made of.
- There is **no built-in table component and no automatic repeat-header**; repeating headers per page must be hand-built with the `fixed` prop or `render`-prop per-page logic.
- The `render` prop on `<Text>` is **called twice** (once during layout, once after page count is known) — side effects in it cause bugs; "Page X of Y" requires it but must be pure.
- Text measurement uses Yoga + Knuth–Plass hyphenation; percentage widths in rows can mis-measure and overflow the page width.

**How to avoid:**
- Build the line-item table as explicitly breakable units: each row `wrap={false}`, header block `fixed` (or re-rendered per page via `render`).
- Treat pagination as a first-class tested feature: a fixture suite engineered to force breaks (3, 7, 12, 40 line items; long descriptions; images) with golden PDF snapshots per break case.
- Use a running line-item count with a page-height budget as a *hint* only — never rely on it for correctness, because the engine decides breaks.
- If pagination fidelity is critical and the spike shows react-pdf cannot deliver it (the #3449 class of bugs is open and engine-level), that is grounds to switch the PDF path to print-CSS (see Pitfall 1) rather than fight the engine.
- Render large documents (30+ pages) in a web worker — react-pdf's own docs warn browser main-thread rendering blocks the UI.

**Warning signs:**
- Any document with >8 line items changes page count between preview and download.
- Manual "break"/"page" props sprinkled through template code (fighting the engine instead of using `wrap`/`fixed` semantics).
- Table rows built from flex rows with no explicit `wrap={false}`.
- QA reports overlap at page bottom on longer invoices.

**Phase to address:**
Phase 1 spike (PDF engine decision — include a pagination torture test in the spike criteria) and the PDF-generation phase (build the break-case fixture suite and golden tests).

### Pitfall 3: IndexedDB data loss and migration mistakes (Dexie)

**What goes wrong:**
Users' invoices, customer lists, and company profiles vanish: a schema change wipes a table, an upgrade function fails and the DB won't open, an index silently disappears, or the browser evicts the origin's storage entirely. For a product whose entire value is "your documents live in your browser," this is a trust-killing, PR-burning failure mode.

**Why it happens:**
Multiple distinct mechanisms (verified from Dexie docs and MDN):
- **Altering a shipped upgrader version.** Dexie docs are explicit: "A version with an upgrader attached must never be altered." Devs edit `version(2).upgrade()` in place instead of adding `version(3)` — devices still on v1 then run a changed v2 path, or the upgrade diff (Dexie ≥3 computes the diff against the *installed* schema) produces undefined behavior.
- **Silent index loss.** Dexie indexes are dropped as soon as they are omitted from a newer `stores()` spec. A schema edit that forgets an index doesn't error — queries on it just break at runtime, and data behind a dropped index can effectively be lost.
- **Non-atomic user-visible state.** Upgrade failure rolls back the transaction and `db.open()` fails — but the app often has already shown the UI; recovery UX is missing.
- **Browser eviction.** MDN documents per-origin storage eviction under quota pressure (LRU eviction of whole origins), plus Safari's aggressive eviction of non-installed ("web app") data and IndexedDB failing entirely in private mode.
- **Transaction lifetime mistakes.** Dexie transactions auto-commit when idle; `setTimeout` or unrelated async work inside a transaction kills it (docs recommend `Dexie.waitFor()` if genuinely needed).
- **No versioning discipline at the start.** Greenfield apps ship `db.version(1)` and never plan for v2, so the first migration is written under fire against unknown user data.

**How to avoid:**
- Adopt Dexie versioning rules from day one: every schema change is a new `version(n)`; never modify a released upgrader; keep prior version declarations; specify `null` to deliberately drop tables.
- Ship **JSON backup/restore** (full workspace export) as a table-stakes feature, not a "nice to have" — it is the only user-facing recovery from eviction/corruption. The PRD already lists it; treat it as core.
- Handle `open()` failure: on upgrade error, offer "export current data" (read-only, before upgrade) and "restore from backup" flows.
- Wrap all multi-write operations (document save = document + line items + counters) in transactions.
- Test migrations on seeded fixture DBs: a CI test that opens v1, v2, ..., vN fixture databases and asserts data integrity at each step.
- Use `navigator.storage.persist()` to request persistent storage (reduces eviction risk) — but never assume it is granted; still keep backups.

**Warning signs:**
- Schema changes implemented by editing `stores()` strings inside the existing `version()` call.
- No versioned fixture DBs in tests.
- Users on Safari/iOS reporting documents that "just disappeared."
- `QuotaExceededError` surfacing in logs.
- No export/backup feature in the requirements (Paperchaser has it — good; keep it mandatory, not optional).

**Phase to address:**
Data-layer phase (schema v1 + migration harness + open-failure UX) and the backup/restore feature phase. The *habit* (never edit a shipped version) starts with the first schema commit.

### Pitfall 4: Undo/redo bugs — snapshot granularity, async state, redo invalidation

**What goes wrong:**
Undo restores the wrong state, redo replays stale data, undoing after autosave resurrects deleted content (or fails to), undo history is lost on reload, or history grows until the tab is unusable. In a document tool, undo bugs read as "the app ate my work."

**Why it happens:**
- **Snapshot granularity mismatch.** Two bad extremes: whole-document snapshots on every keystroke (memory blowup, laggy undo) vs command-per-micro-action (undo undoes half a drag and leaves broken intermediate states).
- **Async state interleaving.** Auto-save (Dexie) and React state updates are async. If the undo stack snapshots Zustand state before a pending Dexie write lands, undo can revert to a state that re-saves deleted data, or undo a change the DB already persisted — the classic "undo doesn't undo" loop with local-first persistence.
- **Redo stack not invalidated.** The redo stack must be cleared the moment a new action occurs after an undo; forgetting this lets users redo onto a divergent timeline, producing duplicated/conflicting documents.
- **History not persisted.** On reload the undo history is gone, so the one time a user needs undo (after a crash) it is unavailable.
- **History persisted naively.** Writing full snapshots of every action to IndexedDB bloats storage and slows saves (couples with Pitfall 3's quota concerns).

**How to avoid:**
- Implement **action/command-based undo** over immutable state: each user action is a discrete, serializable command (addLineItem, moveSection, setField) with an inverse, and document state is derived from an action log (optionally + checkpointed snapshots). This is the industry-standard editor pattern (prosemirror, tiptap, Lexical all use variants).
- **Single source of truth:** the Zustand store is the source for undo; Dexie persistence subscribes to the store (debounced) and never drives it. Undo operates on in-memory state; the persisted DB is a *projection*.
- Invalidate the redo stack on every new action after an undo — one line, unit-tested.
- Persist a *bounded* history: keep the action log per open document, checkpoint full snapshots every N actions or at doc close, drop the log on clean save. On reload, restore the last snapshot (undo-from-crash covers the checkpoint, not the whole session).
- Unit-test the three state machines separately: command/reducer application, autosave debounce, undo/redo transitions.

**Warning signs:**
- Undo implemented as "store the previous state object" (a red flag for async race bugs).
- Redo button enabled after typing a new character.
- Autosave triggers a state replace that clears undo history.
- Undo history stored wholesale in the same persistence as documents.
- Any use of `useEffect` to push state into the undo stack (mount-order dependent, races with async).

**Phase to address:**
Document-engine phase (state model + command pattern decided before the builder UI is built) and the undo/redo feature phase. The decision (command log vs snapshots) must precede the builder — retrofitting undo onto a stateful canvas is a rewrite.

### Pitfall 5: Zustand persist ordering bugs — async hydration, shallow merge, unvalidated rehydration

**What goes wrong:**
On reload, the UI flashes empty/placeholder state before data appears, then state "pops in"; or persisted state silently overwrites fresh defaults; or nested fields are erased after a reload; or corrupt/stale persisted JSON crashes the app at startup.

**Why it happens:**
All three mechanisms are documented Zustand persist middleware behavior (verified from official docs):
- **Async hydration ordering.** With IndexedDB (async) as the storage backend, rehydration happens asynchronously *after* first render. Components render the initial (empty) state, then rehydrated state arrives — visible flash of empty document, or worse, a component that runs once on mount against empty state and never re-runs.
- **Shallow merge default.** The default `merge` is shallow: nested objects in persisted state replace whole sub-objects, erasing fields added since the state was saved. The docs' own example: shallow merge erases a nested `baz` field. A document model with nested line items/customer/settings is exactly the shape that breaks.
- **No runtime validation.** `createJSONStorage` does `JSON.parse` + cast with zero validation — "corrupt, stale, or tampered data will not be caught at runtime." Docs explicitly recommend validating with Zod for production. A truncated write, a schema evolution, or a user-edited backup injected via JSON import can hydrate garbage into the store.
- **Persist/DB write races** with Dexie (two persistence layers disagreeing about which is authoritative — couples with Pitfall 4).

**How to avoid:**
- **Use a Zod-validated rehydrate path** (the docs' production recommendation). Validate the persisted shape before accepting it; on mismatch, fall back to defaults (and preserve the bad payload for recovery).
- **Gate rendering on hydration completion:** use `skipHydration` + `onRehydrateStorage`/`onFinishHydration` to render a loading state until rehydration finishes.
- **Decide one persistence authority.** Recommendation: Dexie is the source of truth for documents/customers/catalog; Zustand persist is for ephemeral UI state (zoom, panel layout) persisted to localStorage (synchronous — eliminates the async-flash class entirely). Avoid persisting the same fact in both.
- Version the persisted state (`version` + `migrate` options exist in the middleware) from the first release.

**Warning signs:**
- FOUC: document list/canvas flashes empty on every reload.
- Nested settings silently reset after reload.
- A schema change in the document model followed by "missing fields" crashes in existing users.
- Both Dexie and Zustand persist writing the same document data.

**Phase to address:**
Data-layer/state phase (persistence-authority decision + hydration gating) — decided before the builder UI so reload behavior is correct from the first vertical slice.

### Pitfall 6: Drag-and-drop complexity — touch-action, scroll containers, zoomed canvas measuring

**What goes wrong:**
On mobile, dragging a section or line item scrolls the page instead of starting the drag; on desktop in a scroll container, drop targets misalign; with zoom/pan on the canvas, items drop at wrong indices; the drag handler eats clicks on inputs inside draggable rows so users can't edit prices in line items.

**Why it happens:**
Verified from dnd-kit docs:
- **`touch-action` is the #1 mobile failure.** The Pointer sensor (dnd-kit default) works on touch only if draggable elements have `touch-action: none`; otherwise the browser's native scroll/zoom wins. Critically, `touch-action` changes after `pointerdown` are **ignored** for that gesture — it must be correct at event start. Recommended pattern: a drag *handle* with `touch-action: none` on the handle only, so the rest of the row stays scrollable and editable.
- **Touch precision.** Touch needs `delay` + `tolerance` activation constraints; a bare distance constraint makes taps indistinguishable from drags, so tapping a row's input field triggers drag.
- **Scroll-container measuring.** dnd-kit measures against scroll containers; a canvas that scrolls *and* zooms/pans (the PRD's zoom feature) means collision-detection rects must account for the canvas transform — a classic source of "dropped at the wrong position."
- **Interactions inside draggables.** Drag event handlers on the row container intercept clicks on inputs/buttons (text selection, price editing, image replace) unless activation is constrained and interactive elements are excluded.
- **Sortable + custom drop logic:** mixing `@dnd-kit/sortable` with canvas-level absolute positioning (sections as layers) requires deciding between list reordering and free positioning; doing both without a coherent model produces janky half-states.

**How to avoid:**
- Use drag handles (with `touch-action: none`) for line items and sections; leave row bodies scrollable/editable.
- Configure PointerSensor with `delay: ~150–200ms` + `tolerance: ~5–8px` for touch, so taps on inputs never start drags.
- Disable drag activation when the pointer starts on interactive elements (`data-no-drag` attributes / `event.target` check), or rely on the handle-only pattern and skip this.
- Account for canvas transform in collision measurement: either measure in the transformed coordinate space (custom `collisionDetection`/`measuring`) or constrain drag to list-reorder (indices) rather than free positioning in v1.
- Test drag on a real touch device/emulator from day one — desktop-mouse-only drag code that "works" is the common false positive.

**Warning signs:**
- Mobile QA: dragging scrolls the page.
- On desktop with a scrollable canvas area, drop position is off by the scroll offset.
- Input fields inside line-item rows don't receive focus/typing.
- Drag code has no touch configuration at all (defaults only).

**Phase to address:**
Builder-UI phase (dnd-kit wiring: handles, sensors, measuring) — include touch-device testing in that phase's acceptance criteria. The drag-handle/activation decision affects the line-item row component design, so it belongs in the builder phase, not later.

### Pitfall 7: Mobile canvas editing — the "mobile-first" requirement quietly becomes desktop-only

**What goes wrong:**
The app *claims* mobile support but editing on a phone is unusable: the live preview canvas is too small to read, editing a line item requires scroll-zoom-pan gymnastics, the keyboard covers the field being edited, text inputs trigger the canvas to re-layout and lose cursor position, and drag handles are unreachable. Desktop works; mobile is a demo-quality afterthought — a direct miss on the PRD's mobile-first constraint.

**Why it happens:**
- Desktop-first architecture carried over: canvas + side panels designed for pointer+mouse+large viewport; mobile gets CSS shrinking instead of a redesign.
- Live re-layout on every keystroke (rendering the full document on input) means the caret jumps / scroll position resets / the canvas repaints under the on-screen keyboard.
- The three-pane model (outline / canvas / properties) is desktop ergonomics; on mobile the PRD's own answer is bottom sheets/drawers + sticky preview, which requires a different interaction architecture, not a responsive stylesheet.
- Zoom/pan on a touchscreen conflicts with text selection and input focus; edit affordances are too small.
- Performance: mobile CPUs make full-document re-render per keystroke visibly laggy (couples with Pitfall 2's "large documents" warning and Pitfall 1's preview cost).

**How to avoid:**
- Design the mobile builder around the PRD's own model from the start: **edit-in-sheet, preview-sticky** — tapping a section/line-item opens a bottom sheet with the form; the canvas stays as a live preview above. Do not design desktop-first and "make it responsive."
- **Stable editing positions:** when a field is focused, freeze canvas layout updates (defer live preview re-layout until blur/scroll-lock) or keep the caret anchored — never let the document re-layout the row being edited under the keyboard.
- `visualViewport` handling for the on-screen keyboard (fields hidden behind the keyboard = classic bug).
- Minimum 44px touch targets for all edit affordances; drag handles clearly separated from tap targets.
- Test on real mid-range Android + iOS devices (not devtools emulation) every phase that touches the builder.

**Warning signs:**
- QA checklist has "mobile" but testing happens in desktop devtools responsive mode only.
- The builder has components that only exist in a "desktop" breakpoint (side panel, hover menus).
- Fields near the bottom of the viewport can't be seen while typing.
- Full-document re-render subscribed directly to per-keystroke state.

**Phase to address:**
Builder-UI phase and its mobile-interaction sub-spec (bottom sheets, sticky preview). The PRD lists "exact mobile interaction patterns" as an open question; the mobile interaction architecture must be a design artifact of the builder phase, not a later port.

### Pitfall 8: Currency/rounding errors in totals

**What goes wrong:**
The invoice grand total is off by cents; subtotal + tax ≠ grand total as shown; the PDF shows one total and the app's summary another; a 100-line invoice with 0.1-unit quantities drifts by dollars; rounding the tax once at the end vs per line produces a total that won't reconcile with the customer's books.

**Why it happens:**
- **Floating point.** `0.1 + 0.2 !== 0.3`; unit price × quantity × (1 − discount%) × (1 + tax%) accumulates representation error. With many line items and rates like 7.7%/19%/21%, the error compounds and shows up as `.9999999` tails or off-by-one cents.
- **Per-line vs aggregate rounding ambiguity.** Two legitimate conventions: round each line to cents then sum, vs sum exact then round once. Invoices in most tax regimes must round **per line** (tax computed on each line's rounded net), so a naive "sum then round" implementation produces totals that don't match per-line amounts — an audit/accounting mismatch, the kind that gets invoices rejected.
- **Tax order.** Discount applied before tax (usually) vs after; shipping taxed vs not; fee taxability — each ordering changes the total. Inconsistent order between the document view and the PDF totals block is a common mismatch.
- **Currency precision.** Multi-currency needs per-currency decimal places (JPY 0, EUR 2, KWD 3); hardcoding 2 decimals corrupts 0-decimal currencies. The PRD lists supported currencies as an open question — the model must not assume 2dp.

**How to avoid:**
- **Integer cents throughout the model** (store quantity as decimal string, unit price as integer minor units per currency), or a decimal library (decimal.js/big.js). Never float for money.
- **Define one total-policy module** used by the canvas, the PDF path, and validation: per-line rounding → per-line tax → sum → apply shipping/fees/discounts in a fixed documented order. One function, exhaustively unit-tested (0.1-quantity cases, 3-decimal rates, negative discounts).
- Round **per line** to match accounting convention; document the choice in an ADR.
- Keep currency as a first-class field on the document with its own decimals/precision; the totals policy reads it.
- Add a self-check: recompute totals from line items at render/export time and assert equality (a totals mismatch is a product-level bug — fail loudly in dev, warn + block download in prod).

**Warning signs:**
- Totals computed inline in a React component's render (spread across the codebase) rather than one policy module.
- Any `.toFixed(2)` scattered in math code.
- Grand total ≠ subtotal + tax in test fixtures.
- No unit tests with 0.1-quantity or 3-decimal-rate fixtures.
- Currency treated as a string label rather than part of the numeric model.

**Phase to address:**
Document-engine phase (totals policy + money model as a core module with exhaustive tests) — it shapes the data model, validation rules, and both render paths; define it before the PDF phase, not during it.

### Pitfall 9: Duplicate document number handling

**What goes wrong:**
Two invoices end up with the same number (a compliance problem in many jurisdictions); or the app *blocks* a duplicate the user legitimately needs (correcting/replacing an invoice often reuses or references a number); or numbering breaks after import/restore; or auto-numbering races when two documents are created quickly.

**Why it happens:**
- **Naive global counter:** a "next number" field incremented on draft creation, not on finalize — drafts that are deleted or duplicated burn/duplicate numbers; two quick creations race (especially with async Dexie writes).
- **No uniqueness definition:** per-customer vs global numbering is undefined (many businesses number per customer or per year); the model hardcodes one without a decision.
- **Import/restore breaks continuity:** after JSON workspace restore, the counter isn't restored (or is), producing collisions with restored documents.
- **Blocking on duplicate:** teams make duplicates hard-error, but real invoicing software (and business practice) needs *warn, don't block* — users legitimately create duplicate numbers for credit notes/replacements, and blocking creates support tickets.
- Validation fires on every keystroke (annoying) instead of on save (actionable).

**How to avoid:**
- Decide the numbering scope explicitly (global sequential default, optional per-customer/per-year) and store it in the document model.
- **Allocate the number at finalize/save, not at draft creation** — drafts stay unnumbered; the counter increments inside the same transaction as the document save (Dexie `rw` transaction over `documents` + `counters` tables), eliminating the race.
- **Warn, don't block:** a duplicate number is a soft warning (validation status) with an explicit "save anyway" affordance; blockers only for missing required fields.
- Restore/export must round-trip the counter: export includes `counters`; import sets next-number = max(existing, counter).
- Validation messaging must explain *why* (compliance guidance per PRD §6.12: guidance only, no legal enforcement).

**Warning signs:**
- Counter incremented in client state (Zustand) not in a transaction with the document write.
- Two documents created in quick succession share a number (async race).
- After restore-from-backup, new documents collide with restored ones.
- Duplicate numbers are impossible to save (hard block).

**Phase to address:**
Document-engine/validation phase (numbering scope + allocate-on-save transaction) and the validation/compliance phase (warn-not-block UX). The transactional allocation belongs with the data-layer save path.

### Pitfall 10: Template system that corrupts document structure

**What goes wrong:**
Switching a template mid-edit wipes or duplicates the user's line items; changing a template's color later retroactively changes old invoices' appearance (or worse, old invoices' structure); a template designed with 3 sections applied to a document with 8 sections mangles the layout; a template update ships with a schema change that breaks every saved document.

**Why it happens:**
- **Templates store structure, not style.** If a template defines sections/line-item layouts and applying it *replaces* the document's content tree, user content is lost or reshaped. The PRD is explicit: templates control *style only, not structure* — violating that is the corruption trap.
- **Live template reference.** Documents stored as `{ template: 'modern', data: {...} }` re-render through the current template definition — editing the template (or shipping a template update) changes every old invoice. Documents must **snapshot the applied styles at creation time** (denormalized), not reference a mutable template by id.
- **Unversioned templates.** A template schema change (new style field, renamed token) with no migration breaks documents saved against older template versions — the same versioning discipline as Pitfall 3, applied to templates.
- **Structural assumptions baked into styles:** templates with hard-coded section counts, fixed image slots, or absolute-positioning assumptions that collide with variable-length content (long company names, many line items, missing logo).

**How to avoid:**
- Enforce **style-only templates at the data-model level**: the document owns its structure (sections/line items); a template is a bundle of style tokens (colors, fonts, header/footer style, watermark style) applied at render/export time. Switching templates only swaps tokens — structure untouched. Enforce with a model rule, not a convention (validate on apply: template application may not add/remove/reorder content nodes).
- **Snapshot styles into the document** on create/apply (store the resolved style object in the document record); template edits affect only new documents. If template updates should propagate, that is an explicit versioned migration, never implicit.
- Version templates (templateVersion in the doc) with a migration path for old docs when a template's *schema* changes.
- Never let a template's style definitions include structural directives (hidden sections, conditional rendering of content) in v1 — that is the slippery slope to corruption.

**Warning signs:**
- Applying a template resets the line items / content in any test.
- Changing a template's color in the app changes already-saved invoices' PDFs.
- Templates shipped as full document JSON ("template = example invoice with content").
- Template code branches on `if (sectionCount === 3)`.

**Phase to address:**
Template/branding phase (style-token model + snapshot-on-apply + template versioning) — but the *constraint* (structure owned by document, style by template) must be encoded in the document data model from the document-engine phase, or the template phase will retrofit corruption.

### Pitfall 11: PWA caching pitfalls — stale service worker, data-losing auto-update, cached index.html

**What goes wrong:**
Users keep running an old app version (stale SW); worse, a service-worker auto-update **reloads the browser tab mid-edit and the user loses the invoice they were typing**; a cached `index.html` never picks up new builds; dev mode works fine but production updates are broken; offline mode serves a version that can't read the IndexedDB schema written by the newer app (couples with Pitfall 3).

**Why it happens:**
- Verified from vite-plugin-pwa docs: `registerType: 'autoUpdate'` causes the SW to take control and **reload all open tabs** when a new version is detected — the docs explicitly warn: "the user can lose data in any browser windows/tabs in which the application is open and is filling in a form," and recommend the **`prompt`** strategy for form apps. Paperchaser is a form app.
- The docs also warn that **changing from `autoUpdate` to `prompt` later "can be a pain"** — a migration you don't want to do after users have the old SW cached.
- `index.html` precached without care + `autoUpdate` disabled = users on stale bundles forever; conversely aggressive SW caching of runtime requests for an SPA can serve old JS that mismatches new IndexedDB code.
- Dev vs build behavior differs (SW only in build); teams "test" PWA in dev and ship broken production updates.
- Versioned API/database coupling: new app code writing a new Dexie schema while an old SW still serves old JS to a second tab = two schema versions on one origin (corrupts data — combine with Pitfall 3).

**How to avoid:**
- **Use `registerType: 'prompt'` from day one** (vite-plugin-pwa docs' recommendation for form apps): show an in-app "update available — reload" banner the user can defer until they've saved. Do not ship `autoUpdate` first and migrate later.
- Keep `cleanupOutdatedCaches: true` (default) so old precaches don't pile up.
- Ensure `index.html` isn't frozen: workbox generateSW default with `navigateFallback` is fine, but verify a network-first/fallback policy for navigation so new builds reach users.
- Never let the SW cache `POST`/mutating requests — the plugin precaches GET assets only by default; keep it that way (the app has no API, but don't add runtime caching that could capture document writes).
- **Test SW behavior only in production builds** (devOptions.enabled is opt-in and can mask issues); run an update-flow QA script: build v1 → open → build v2 → reload → verify prompt/reload behavior and data intact.
- Schedule the PWA feature near the end (pre-launch polish phase): it touches the same persistence as everything else, and its failures are data-loss failures.

**Warning signs:**
- `registerType: 'autoUpdate'` in the config for a form app.
- No update prompt/flow in the UI.
- Testers "don't see new versions" on staging.
- Any SW code manually caching POST requests or API routes.
- PWA tested only in `npm run dev`.

**Phase to address:**
PWA/offline phase (near the end; prompt-strategy registration + update banner) — with a hard gate: the update flow must be tested with a v1→v2 schema migration in place (ties to Pitfall 3).

### Pitfall 12: TanStack Start complexity for a no-backend app

**What goes wrong:**
The project ships TanStack Start (a full-stack, SSR/streaming/server-functions framework) to build an app with *no backend*, and absorbs: a server build pipeline, hydration, deployment to a Node server (or fighting static prerendering), SSR-only-API traps (accessing `window`/IndexedDB during render), and a large framework surface for zero feature benefit — while the actual product risk (PDF parity, data layer) gets starved of attention.

**Why it happens:**
- The PRD pinned TanStack Start, and "keep the PRD stack" is the default. But the framework's **own docs** say: "if you know with certainty that you will not need any of the above features [SSR, server routes, server functions, streaming], then you may want to consider using TanStack Router alone." A no-backend, local-first app is precisely that case.
- **Framework-stage risk:** TanStack Start is in Release Candidate stage ("feature-complete... not bug-free"), per its own overview — a moving target underneath a greenfield product.
- Local-first libraries (Dexie, Zustand persist, the canvas) run client-only; every server-rendered route must guard against accessing browser APIs — a permanent class of bugs (hydration errors, `window is undefined`) that a plain SPA never has.
- Deployment: static hosts need SPA mode / prerendering config (`/_shell.html`, 404 rewrites, prerender jobs) — *more* config than a plain Vite SPA build, for the same static result.
- Misunderstood value: "Start" is assumed free; it isn't — it is a server-runtime decision that contradicts the product's core constraint (no server, privacy-first).

**How to avoid:**
- In the **Phase 1 spike**, treat "keep TanStack Start vs plain Vite SPA + TanStack Router" as a first-class decision with an ADR, not a default. Criteria: does the product need any server feature? (No — accounts, sync, and email are all out of scope.) Does static hosting matter? (Yes — privacy-first local-first implies simple static deploy.)
- If Start is kept (e.g., the team wants it for a future hosted version), use SPA mode + prerendering and add a lint/test guard that no route touches client-only APIs during SSR.
- Recommended: **Vite SPA + TanStack Router** — the docs themselves point to it; it keeps the PRD's TanStack investment (router, form, query) while dropping only the server half.
- Ensure `window`/IndexedDB access is always behind `typeof window !== 'undefined'` / client-only guards if any SSR path exists at all (including the PWA `virtual:pwa-register` import, which the plugin docs flag for SSR/SSG).

**Warning signs:**
- Any "SSR" or "server function" file in the repo for a feature that is client-only.
- Deployment requires a Node server/edge runtime for an app whose PRD says "no backend."
- Hydration-mismatch errors in the console.
- Framework upgrades churning the app's core files (sign of betting the product on an RC framework).

**Phase to address:**
Phase 1 spike (framework decision + ADR). This is a *cost* pitfall rather than a data-loss pitfall, but it taxes every later phase, so the decision must be made before Phase 2 scaffolding.

## Technical Debt Patterns

Shortcuts that seem reasonable but create long-term problems.

| Shortcut | Immediate Benefit | Long-term Cost | When Acceptable |
|----------|-------------------|----------------|-----------------|
| HTML preview + separate react-pdf tree for output | Fast preview, "real PDF" feel | Two layout engines to keep in sync forever; PRD §6.9 fails; every visual change double-implemented | Never — if react-pdf is kept, both must consume the same serialized document model |
| Storing documents as `{template: 'modern'}` live references | Tiny storage, easy template redesign | Template edits mutate old invoices; no snapshot isolation; corruption vector | Never — snapshot styles into the document at create/apply |
| Editing Dexie `stores()` in-place for schema changes | Fast iteration pre-launch | Silent index drops, broken upgraders for real users | Only before the first user-facing release; never after |
| Undo = previous-state snapshot in Zustand | 30 minutes to implement | Async autosave races, memory blowup, wrong undo | Never for a document editor; command log is the pattern |
| Money as JS `number` with `.toFixed(2)` | Zero dependencies | Off-by-cents totals, audit mismatch, currency-precision bugs | Never for money in an invoice product |
| Auto-increment document number in client state | Simple | Races on rapid creation, breaks after import, duplicates | Never — allocate in the save transaction |
| `registerType: 'autoUpdate'` for the PWA | Zero UI work | Reloads tabs mid-edit; users lose work; hard to migrate to prompt later | Never for a form-heavy app |
| "Responsive CSS" instead of a mobile interaction design | Looks mobile in devtools | Unusable phone UX; mobile-first requirement unmet | Never — mobile is a core constraint (PRD §3) |
| Drafts numbered at creation | Simple UX | Duplicate/burned numbers when drafts die or duplicate | Acceptable only with a visible "unfinalized" state and allocation at finalize (preferred: don't number drafts at all) |
| Versioning templates by copying the old one | Works today | Template bloat, no migration path, docs reference dead versions | Acceptable until the first template schema change; then migrate properly |

## Integration Gotchas

Common mistakes when connecting the pieces of this stack.

| Integration | Common Mistake | Correct Approach |
|-------------|----------------|------------------|
| @react-pdf/renderer + fonts | Registering fonts, then rendering before they load — PDF metrics/layout change after preview | Await `Font.register` promises / asset fetch before first render; react-pdf fetches fonts async and blocks layout until done |
| @react-pdf/renderer + images (logo, line-item images) | Image that loads late shifts layout between preview and export | Preload images into the doc model (or use `wrap={false}` + explicit sizes) so layout is deterministic |
| Zustand persist + IndexedDB (custom storage) | Async rehydration flash; shallow-merge clobbering nested docs | Validate with Zod on rehydrate, deep-merge, gate render on hydration; or keep persist for UI prefs (localStorage) and Dexie for data |
| Dexie + service worker (PWA) | Old SW serves old JS writing new schema (or vice-versa) | Version SW control tightly; `prompt` update strategy; test v1→v2 migration under a live SW |
| dnd-kit + inputs inside draggable rows | Drag starts when user tries to type in a price field | Drag-handle-only activation; PointerSensor delay+tolerance; `touch-action: none` on handles |
| dnd-kit + zoomed/panned canvas | Drop indices wrong because collision rects ignore the canvas transform | Custom `collisionDetection`/`measuring` in transformed space, or list-reorder-only in v1 |
| TanStack Router + IndexedDB/local-first | Router preload/loader accessing browser APIs during SSR | Client-only guards; or plain SPA (no SSR) so the question disappears |
| vite-plugin-pwa + TanStack Start SSR | `virtual:pwa-register` imported at module top-level breaks SSR | Dynamic import guarded by `typeof window !== 'undefined'` (per plugin docs) |
| JSON import + validation | Accepting arbitrary JSON into the store/DB → garbage documents, crashes | Zod schema validation at the import boundary, with clear per-field errors; same validator as export |

## Performance Traps

Patterns that work at small scale but fail as usage grows.

| Trap | Symptoms | Prevention | When It Breaks |
|------|----------|------------|----------------|
| Full PDF render on every keystroke (react-pdf path) | Typing lags; tab unresponsive; mobile jank | Throttle/debounce export render; render preview from the document model, not per-keystroke PDF (print-CSS path is browser-native) | ~1–2s render threshold / any mobile device |
| Whole-document state snapshot per action for undo | Memory climbs; save bloat | Command log + periodic checkpoints; bounded history | ~100+ line items or long sessions |
| Re-rendering the entire canvas on any state change | Every keystroke repaints all pages | Selector-based subscriptions (`useStore` selectors), memoized page components, keyed rendering | 5+ pages with images |
| Unbounded history persisted to IndexedDB | Storage quota; slow autosave | Bounded in-memory history; checkpoint snapshots; drop log on clean save | Weeks of use / many documents |
| Full-table reads for the dashboard (`toArray()`-style) | Slow dashboard on many documents | Indexed queries, limit + pagination, Dexie `where()` on indexed fields | ~1k+ documents |
| react-pdf main-thread rendering of 30+ page docs | "Unresponsive page" browser dialog | Web-worker rendering (react-pdf docs' own recommendation) | ~30 pages (docs cite this threshold) |
| Images stored as base64 in IndexedDB without size limits | Quota blowup; slow saves; eviction risk | Downscale logos/item images on upload; cap dimensions/bytes; store Blobs not base64 strings | Logos + many line-item images |
| Selector-less `useStore(state => state)` in every component | Whole tree re-renders per keystroke | Selector APIs / fine-grained subscriptions | 20+ components in the builder |

## Security Mistakes

Domain-specific issues beyond general web security (this app is no-backend, so the surface is small but real).

| Mistake | Risk | Prevention |
|---------|------|------------|
| JSON import/restore without schema validation | Malicious/backup files hydrate garbage or malicious payloads (XSS via `dangerouslySetInnerHTML`-rendered fields like notes/description) | Zod-validate every imported document; never render user text as HTML without escaping; CSP header; sanitize on render |
| Rendering user-supplied content (company name, notes, line-item description) as rich HTML | Stored XSS — a "customer" field containing `<img onerror=...>` executes on export/render | Escape all text fields; if rich text is needed, use a sanitized editor output (allow-list), never raw HTML |
| Logo upload by URL | SSRF-ish/exfiltration vector: URL fetch of arbitrary origins, tracking pixels in exported PDFs | Prefer file upload (downscaled) over URL logo; if URL logos are kept, validate scheme/host and note the privacy leak |
| Imported template/document JSON with external font/image URLs | Documents re-fetch remote assets at render time → data exfiltration + layout instability offline | Bundle fonts locally; snapshot/embed images; CSP `img-src`/`font-src` restrictions |
| No export privacy awareness | A backup file containing customer PII + bank details sits in Downloads/cloud drive unencrypted | Backup UX warning + (optional, phase-later) password-encrypted export; guidance in the compliance checklist |
| Service worker caching sensitive document data | Documents cached in SW caches outliving IndexedDB, surviving clear-data flows | Never route document reads through SW caching; documents live in IDB only; SW caches app-shell assets only |
| Relying on localStorage for any document data | XSS can read it; 5MB cap; evicted silently | Documents in IndexedDB (Dexie); localStorage only for non-sensitive UI prefs |

## UX Pitfalls

Common user experience mistakes in this domain.

| Pitfall | User Impact | Better Approach |
|---------|-------------|-----------------|
| "Identical preview/output" violated (Pitfall 1) | User arranges a one-page invoice; download is two pages — PDF emailed to a client wrong | Parity by construction (print-CSS) or golden tests on the PDF path |
| Autosave without visible save state | "Did it save?" anxiety; closing tab loses work | Visible save indicator + "recovered draft" toast on reload + backup reminders |
| Blocking validation (duplicate number, negative qty) instead of guiding | User can't do a legitimate thing (duplicate number for a correction); friction on every keystroke | Warn-not-block; validate on save/blur, never every keystroke; compliance *guidance* per PRD §6.12 |
| Mobile: bottom-sheet keyboard occlusion | Fields hidden behind the on-screen keyboard; can't see what you type | `visualViewport` positioning; scroll field into view; sticky preview collapses when editing |
| Drag affordances invisible on mobile | Users don't know rows reorder; long-press hijacks scrolling | Visible drag handles (44px), explicit "reorder" mode on mobile, or tap-and-hold with visual feedback |
| Totals updated only on blur/save | User sees stale totals while editing qty — thinks math is broken | Live totals (computed, derived state) at typing speed; cheap because totals derive from one policy function |
| Empty states unexplained | First-run confusion: "where do I put my company logo?" | Dashboard quick-start checklist; template gallery first-run; onboarding in under 5 min per core value |
| Print/export mismatch (A4 assumption) | US-Letter users get cut-off edges; A4 users get wide margins | Page size as a first-class document setting (PRD lists it); preview reflects the chosen size |
| Undo across autosave boundaries | Undo reverts a save → re-save resurrects deleted content | Undo over in-memory state; persistence is a projection (Pitfall 4) |

## "Looks Done But Isn't" Checklist

Things that appear complete but are missing critical pieces.

- [ ] **PDF parity:** Preview matches PDF for the *torture cases* (long company name, 12 line items, accented text, logo present, watermark) — not just a 2-line test doc. Verify with golden-image diff.
- [ ] **Pagination:** Line-item table with 40 items, a mid-table page break, and a repeated header on page 2. (react-pdf has no automatic repeat-header.)
- [ ] **Print margins:** `@page` margins and mm-accurate content box verified in Chrome AND Safari AND the print dialog, not just the preview pane.
- [ ] **Autosave crash recovery:** Close the tab mid-edit, reopen, confirm the draft and a "recovered" notice. (No-backend apps have no server copy — this is the only safety net.)
- [ ] **Backup/restore round-trip:** Export workspace → wipe IndexedDB → restore → verify documents, counters, template snapshots, and image blobs all survive. Also: restore into a DB that already has data (merge policy?).
- [ ] **Migration test:** Seeded v1 DB opens under v2 code without data loss — automated, not manual.
- [ ] **Undo/redo across autosave:** Edit → wait for save → undo → confirm the document in IndexedDB also reflects the undo (no resurrection).
- [ ] **Hydration:** Reload with persisted documents; document list must not flash empty (Zustand/Dexie async-hydration gate).
- [ ] **Mobile drag:** Line-item reorder works on a real touch device; the price field inside the row is still editable.
- [ ] **Currency:** 0.1-quantity × 3-decimal-rate fixtures reconcile to the cent; per-line rounding matches the PDF.
- [ ] **Duplicate number:** Save with a duplicate → warning shown, save allowed, warning clearly explained.
- [ ] **PWA update flow:** v1 open in two tabs → deploy v2 → prompt appears, user defers, saves, then updates without data loss. (Never `autoUpdate`.)
- [ ] **Offline full-cycle:** Load app online → go offline → create a complete invoice with logo → export PDF → confirm everything works from cache/IDB.
- [ ] **JSON import hardening:** Import a truncated file, a file with extra/unknown fields, and a file with malicious HTML in a text field — all must fail gracefully with a clear message, no crash, no XSS.

## Recovery Strategies

When pitfalls occur despite prevention, how to recover.

| Pitfall | Recovery Cost | Recovery Steps |
|---------|---------------|----------------|
| IndexedDB data loss / migration failure | HIGH (user data) | JSON export before any upgrade attempt (read-only pass); restore-from-backup flow; keep the corrupted DB file for diagnosis; storage-manager guidance for evicted origins |
| PDF/output mismatch discovered late | MEDIUM | If print-CSS: fix CSS and re-generate (no data change). If react-pdf: re-architect the shared document model — this is the rewrite; contain it by having the model be pure data from day one |
| Undo/redo corruption | MEDIUM | Discard in-memory history; rebuild from last checkpoint; ensure persistence is a projection so the DB is still consistent |
| Duplicate-number mess after import | LOW | Rebuild counters = max(existing); offer "renumber" utility for the affected docs with user confirmation |
| Template corruption of old documents | MEDIUM | Snapshotted styles mean corruption is limited to docs saved without snapshots (pre-fix); migrate those via template versioning |
| PWA stale-version data schema mismatch | HIGH (data) | `prompt` strategy means the user controls reload; if already shipped autoUpdate: add a save-on-beforeunload/visibilitychange hook as a mitigation before migrating to prompt |
| Stored XSS shipped | HIGH (trust) | Immediate sanitization pass + CSP; rotate/clear affected stored fields; communication plan |
